# PlanIt 백엔드 기술 스택

## 1. 언어 - Java

### 언어 선정 이유

우리 서비스는 회원, 여행 일정, 방문 장소 등을 관리하고 일정 수정 권한이나 여행 날짜 검증과 같이 여러 업무 규칙을 구현해야 한다. Java의 객체지향 특성을 활용하면 각 객체의 책임을 나누고, 관련 데이터와 동작을 함께 관리할 수 있다고 판단했다.

### Java란?

자바는 단순성, 안정성 및 이식성을 중시하는 고급 객체 지향 프로그래밍 언어.

> **이식성?** 
서로 다른 실행환경을 가진 시스템 간에 프로그램을 옮겨서도 실행할 수 있는 것
**왜 이식성이 높을까?** 
자바는 JVM 위에서 동작하기 때문에 **운영체제와 상관없이 작동이 가능**하기 때문
> 

### 객체 지향 언어란?

데이터와 기능을 객체로 묶고, 객체 간 상호작용을 중심으로 프로그램을 구성하도록 지원하는 언어

ex) 계좌 객체에 잔액이라는 데이터와 입출금이라는 기능을 묶어 관리할 수 있음

#### 특징

- **추상화** : 복잡한 구현을 감추고 필요한 기능을 드러냄
- **상속** : 기존 클래스의 속성과 동작을 물려받아 확장하거나 재정의
- **다형성** : 동일한 메서드를 호출해도 실제 객체에 따라 다르게 동작함
- **캡슐화** : 데이터와 기능을 하나로 묶꼬, 외부 접근을 제한해서 객체 상태를 보호함

#### SOLID 원칙

- **SRP - 단일 책임 원칙**
    
    클래스는 하나의 책임을 가지며 하나의 변경 이유만을 가지도록 설계해야 함
    
- **OCP - 개방·폐쇄 원칙**
    
    기능 확장에는 열려 있고, 기존 코드 수정에는 닫혀 있어야 함
    
- **LSP - 리스코프 치환 원칙**
    
    자식 클래스는 언제나 부모 클래스를 대체할 수 있어야 함
    
- **ISP - 인터페이스 분리 원칙**
    
    클라이언트는 자신이 사용하지 않는 메서드에 의존하지 않아야 함
    
- **DIP - 의존 역전 원칙**
    
    상위 정책과 하위 구현에 직접 의존하지 않고, 양쪽 모두 인터페이스나 추상 클래스에 의존해야 함
    

### Java 특징

- 정적 형식으로 컴파일 시, 런타임에서 엄격한 형식 검사를 적용해 오류를 줄이는 데 도움을 줌
    - **파이썬** : 동적 형식을 사용해서 빠른 개발에 더 쉬움
    - **C++** : 시스템 하드웨어를 더 세밀하게 제어할 수 있기 때문에 성능이 중요한 애플리케이션에 적합함
- 자바 구분은 C++과 비슷하지만 더 단순하고 유지 관리하기 쉬움
- 가비지 컬렉션을 통한 자동 메모리 관리 기능이 있기 때문에 메모리 관련 문제를 줄여줌

**가비지 컬렉션**

개발자가 프로그램 코드로 메모리를 명시적으로 해제하지 않기 때문에 GC가 더이상 사용되지 않는 객체를 자동으로 메모리에서 제거하는 JVM의 메모리 관리 기능

stop-the-world가 발생하면 GC를 실행하는 쓰레드를 제외한 나머지 쓰레드는 모두 작업을 멈춤 → GC 작업을 완료한 이후에야 중단했던 작업을 다시 시작

### 작동 방식

자바 소스 코드는 javac를 통해 바이트코드로 변환됨 → JVM은 이를 해석해 실행하고 자주 실행되는 부분은 JIT가 기계어로 변환해 속도를 높임

이 바이트코드는 플랫폼 독립적이어서 JVM이 설치된 어떤 시스템에서도 실행 가능함

> 
> 
> 
> #### JVM이란?
> 
> - 바이트 코드를 실행해주는 가상 머신
> - 윈도우, 맥, 리눅스같은 운영체제 차이를 신경쓰지 않고 실행될 수 있도록 중간에서 실행환경을 제공함
> 
> #### JIT란?
> 
> - Just-In-Time 컴파일러. 실행 중 바이트코드를 CPU가 직접 실행할 수 있는 기계어로 변환함
> - 자주 실행되는 메서드나 반복 구간을 찾아 컴파일하고 최적화해 실행 속도를 높임

### 자바 버전 - 21

JDK : Java 프로그램을 개발하고 실행할 때 필요한 도구의 묶음(컴파일러인 javac, 실행환경인 JVM, 디버깅·진단 도구 등 포함)

#### 선정 이유

장기적인 유지보수와 업데이트를 고려해서 LTS 버전인 Java 8, 11, 17, 21, 25를 검토했다.

우리 프로젝트에서는 필요한 기능을 구현하면서 향후 동시 요청이 증가했을 경우 대응할 수 있도록 Java 21을 선택하였다. Java 21은 LTS 버전이고, 가상 스레드를 정식으로 제공하기 때문에 I/O 대기로 인한 스레드 부족이 발생했을 경우에 활용할 수 있다. 

> **I/O 대기란?**
프로그램이 DB·네트워크·파일 등에 작업 요청하고 결과가 돌아올 때까지 기다리는 상황

우리 서비스에서는 지도, 날씨를 조회할 때 외부 API를 호출하고 응답을 기다림
→ 새로운 요청이 들어오면 처리에 사용할 스레드가 부족해짐
> 

가상 스레드는 처음부터 적용하기보다는 플랫폼 스레드 풀 기반으로 먼저 구현한 뒤에 필요할 때 도입하려고 한다.
우리 서비스 특성 상 연휴와 같은 날짜에 여행을 가려는 사용자가 많아질 경우나 여러 사용자에게 알림을 보낼 경우와 같이 한 번에 몰릴 가능성이 충분하다고 판단했기 때문에 DB 조회나 외부 API 응답을 기다리는 요청이 많아질 수 있다. 

이때 CPU에는 여유가 있지만 요청 처리 스레드가 부족한 상황이라면 기존 동기식 코드를 유지하며 동시성을 해결할 수 있는 방법으로 검토하려고 한다.

> 
> 
> 
> **플랫폼 스레드 풀:** 스레드를 여러 개 준비해 두고 작업이 들어올 때 재사용하는 구조
> 

Java 25 도입 시 IDE 디버거와 라이브러리 등 주변 도구의 호환성 검증이 필요하다고 판단했다.

실제로 특정 IntelliJ 버전에서 Java 25 프로세스에 디버거를 연결하지 못하는 문제가 있었고, 이후 IDE 업데이트로 수정된 사례를 확인했다. 따라서 25 버전보다는 디버깅에 더 안정적인 21을 사용하기로 결정했다.

💡

**스레드란?**

하나의 프로그램 내에서 동시에 실행될 수 있는 독립적인 실행 흐름 단위

**플랫폼 스레드 풀이란?**

작업을 처리하기 위한 스레드를 매번 새로 생성하지 않고, 미리 만들어둔 스레드 집합을 재사용하여 작업을 처리하는 구조

**동작 방식**

작업이 들어오면 대기열에 저장되고, 유휴 상태의 스레드가 해당 작업을 꺼내 실행함
→ 작업이 끝난 스레드는 제거되지 않고 다시 풀로 돌아가 다음 작업을 기다림
→ 기다리는 동안 해당 플랫폼 스레드가 점유됨

자신의 수명 동안 OS 스레드를 점유하기 때문에 사용 가능한 플랫폼 스레드 수는 OS 스레드 수로 제한됨

**가상 스레드란?**

OS Thread와 1:1로 연결되지 않고, Carrier Thread를 통해 CPU 위에서 실행된다.

**동작 방식**

가상 스레드에서 실행되는 코드가 블로킹 I/O 작업을 호출하면 자바 런타임은 해당 가상 스레드를 일시 중단하고 다시 시작할 수 있을 때까지 기다림. 일시 중단된 가상 스레드와 연결된 OS 스레드는 다른 가상 스레드를 위한 작업 수행 가능함

→ (대기 시간이 긴 동시 작업이 많은) 고처리량 동시 실행 애플리케이션에서 사용하면 좋음

가상 스레드는 속도가 아닌 **확장성을 제공하기 위해 존재함**

</aside>

### 고려해야 할 점

하지만 Java 21에서 가상 스레드를 도입할 경우에 고려해야 할 문제는 피닝(Pinning)이다. 가상 스레드는 실제 실행을 담당하는 플랫폼 스레드인 캐리어 스레드 위에서 동작한다. I/O 응답을 기다리는 동안에는 캐리어 스레드를 놓아줘 다른 가상 스레드가 사용할 수 있게 한다. 

**피닝 :** 가상 스레드가 캐리어 스레드에 분리되지 못하는 상태.

> **캐리어 스레드란?**
가상 스레드의 코드를 실제로 실행하는 플랫폼 스레드. JVM이 가상 스레드를 캐리어 스레드에 올려 실행함

**흐름**
가상 스레드 A가 캐리어 스레드에서 실행됨 → A가 지원되는 I/O 작업 결과 기다리면 캐리어에서 분리됨 → 해당 캐리어는 다른 가상 스레드 B를 실행함 → A 대기가 끝나면 사용 가능한 캐리어에서 실행 이어감
> 

Java 21에서는 가상 스레드가 synchronized 내부에서 긴 블로킹을 수행하면 대기하는 동안 캐리어 스레드까지 묶일 수 있다. 이런 상황이 자주 발생하면 다른 요청을 처리할 자원이 부족해져서 가상 스레드의 동시 처리 이점이 줄어들 수 있다. 

> **synchronized란?**
한 번에 하나의 스레드만 해당 자원에 접근할 수 있도록 제한함.
단순한 구조에서 편리하게 사용할 수 있음
**사용 이유?**
여러 스레드가 동시에 같은 메모리 공간에 접근하면 데이터 충돌이나 예기치 않은 결과가 발생할 수 있어서
> 

이를 방지하기 위해 외부 API 호출이나 DB 조회 같은 작업이 잠금 안에서 오래 수행되는지 확인해 길고 자주 피닝이 확인된 구간엔 ReentrantLock 적용을 검토할 예정이다.

> **ReentrantLock이란?**
동일한 스레드가 여러 번 안전하게 진입할 수 있는 락.
복잡한 동기화 조건, 정밀한 락 제어, 스레드 인터럽트 대응, 락 시도/포기 흐름 분기 등의 상황에 명시적으로 동작하도록 설계됨
> 

| **항목** | synchronized | ReentrantLock |
| --- | --- | --- |
| 락 획득 방법 | 자동 (블록 진입 시 획득) | 명시적 (lock(), unlock() 사용) |
| 락 해제 방법 | 자동 (블록 종료 시 해제) | 명시적 (unlock() 호출 필요) |
| 락 획득 대기 중 인터럽트 처리 | 불가능 (인터럽트 무시) | 가능 (lockInterruptibly() 사용 가능) |
| 락 획득 시도 및 실패 처리 | 불가능 | 가능 (tryLock()으로 대기 없이 시도 가능) |
| 조건 변수 (Condition) 사용 | 불가능 (wait/notify만 사용 가능) | 가능 (newCondition()으로 세분화 가능) |
| 공정성 (FIFO 보장) 설정 | 불가능 | 가능 (new ReentrantLock(true)) |
| 재진입 가능 여부 | 가능 | 가능 |

## 2. 프레임워크 - Spring Boot

### 선정 이유

우리 프로젝트는 여행 일정과 DB 접근, 외부 API 연동, 알림 발송 등 여러 기능을 구현해야 하므로 공통 설정의 부담을 줄이고 서비스 기능 개발에 집중할 수 있는 Spring Boot를 선택했다.

자동 설정과 Starter를 통해 웹·DB 연동에 필요한 구성을 간편하게 끝내고, 내장 서버를 이용해 애플리케이션을 독립적으로 실행할 수 있어 실행·배포 구성을 단순화할 수 있다.

### Spring Boot란?

- 스프링 애플리케이션을 빠르고 쉽게 개발할 수 있도록 설정과 배포를 자동화한 프레임워크
- 기존 Spring 기반이면서 개발자가 애플리케이션을 더 간단하고 직관적으로 만들 수 있음

### Spring Boot 특징

- 자동 설정, Starter 의존성 관리, 내장 서버 제공해 복잡한 환경 설정 과정 줄임
    - spring-boot-starter-web : 웹 애플리케이션 개발에 필요한 라이브러리 묶음
    - DispatcherServlet : Spring MVC의 핵심 서블릿. 클라이언트 요청을 받아 알맞은 컨트롤러에 전달하고 응답 되돌려줌
    - 기본 에러 페이지 : 오류 발생 시 개발자가 별도 설정하지 않아도 에러 확인 가능
    - Jackson : 자바 객체를 JSON으로 변환하거나, JSON을 자바로 변환해주는 라이브러리 → REST API 개발에서 필수적으로 사용됨
- Actuator 지원 : 애플리케이션의 상태와 지표 확인하고 운영 중 모니터링 가능

### Spring Boot 구조

흐름 : 클라이언트 → 컨트롤러 → 서비스 → 레포지토리 → 데이터베이스 

- **Controller** : 클라이언트의 요청을 받아 서비스 기능 호출해 응답을 반환하는 계층
    
    ex) “여행 일정 저장해줘”라는 요청을 받아 service에 전달하고, 저장 결과를 응답함
    
- **Service** : 비즈니스 규칙을 적용하고 필요한 작업 조합해 기능을 수행하는 계층
    
    ex) 여행 날짜가 올바른지, 저장할 권한이 있는지 확인하고 일정 저장 진행함
    
- **Repository** : DB에 접근해 데이터를 생성, 조회, 수정, 삭제하는 역할
    
    ex) 여행 일정을 DB에 저장하거나, 저장된 일정을 DB에서 찾아옴
    
- **DTO** : 클라이언트와 서버 또는 계층 사이에서 필요한 데이터를 전달하기 위한 객체
    
    ex) 여행 날짜, 여행지처럼 요청이나 응답으로 주고받을 데이터를 담음
    
- **Entity** : JPA에서 DB 테이블과 매핑되며 고유 식별자를 가진 영속성 관리 대상 객체
    
    ex) DB에 저장할 여행 일정의 구조를 코드로 표현, 일정 날짜 등의 값을 가짐
    

#### Spring MVC

- 스프링 프레임워크에서 제공하는 웹 애플리케이션 개발을 위한 아키텍처
- Model-View-Controller 패턴 기반으로 함
    
    → 웹 요청을 처리하는 과정을 역할별로 분리해 코드의 복잡성 줄이고 유지보수성 높임
    
    - Model : 화면에 보여줄 데이터와 비즈니스 로직을 담는 영역
    - View : 최종적으로 사용자에게 보여지는 화면
    - Controller : 사용자의 요청을 받아 처리 흐름을 제어하는 역할
    
    #### 동작 흐름
    
    1. 사용자가 브라우저에 요청 보냄
    2. 그 요청을 DispatcherServelet(프론트 컨트롤러)이 받음
        1. 모든 요청과 응답을 한 곳에서 관리
        2. 어떤 컨트롤러가 요청을 처리할지 찾아 위임
    3. 컨트롤러는 필요한 비즈니스 로직 실행하고 Model에 데이터 담음
    4. Model은 준비된 데이터를 컨트롤러로 반환
    5. 컨트롤러는 뷰 이름을 DispatcherServlet에 반환
    6. DispatcherServlet은 View Resolver를 통해 실제 뷰 템플릿 결정
    7. View는 Model 데이터 반영해 최종 HTML 생성
    8. DispatcherServlet은 이 HTML을 클라이언트(브라우저)에 응답

## 3. DB - MySQL

### DB란?

데이터를 저장, 관리, 검색할 수 있도록 구조화된 시스템

### DB 구조

- 테이블 : 데이터를 행과 열로 구성
- 스키마 : 데이터의 구조와 규칙을 정의
- 인덱스 : 데이터 검색 속도를 높임
    
    > **인덱스**
    테이블에 대한 조회 동작의 속도 높여주는 자료구조
    
    **왜 사용하는가?**
    인덱스가 없으면 데이터 찾을 때 모든 행 돌아야 함. But 인덱스로 관리하면 빠르게 소거하면서 조회 가능하기 때문에
    
    **주의점**
    - 인덱스는 조회 성능을 크게 향상시키지만, 데이터가 삽입, 수정, 삭제될 때마다 인덱스 구조도 함께 변경되어 쓰기 성능에는 오버헤드가 발생할 수 있음
    - B+Tree 인덱스는 정렬 기반 구조이므로 LIKE ‘%검색어’와 같이 앞부분 고정되지 않은 검색에서는 인덱스 사용 불가함
    
    → 조회가 빈번하고 값 변경이 상대적으로 적은 컬럼에 사용하는 것이 적합함
    
    **조회 성능 ↔ 쓰기 성능의 트레이드오프**
    조회 시 빠른 탐색 가능하지만, 데이터 삽입,수정,삭제될 때마다 테이블 데이터, 인덱스 구조도 함께 갱신되어야 함 → 인덱스 많을수록 쓰기 작업의 비용 증가하고 페이지 분할 등 오버헤드 발생할 수 있음
    
    **저장 공간 증가 ↔ 관리 비용 증가**
    인덱스는 실제 디스크 공간 차지하는 데이터 구조라, 수가 늘어날수록 디스크 사용량 증가, 캐시 효율 저하와 같은 운영 비용 함께 증가함
    > 

### DBMS

다수의 사용자들이 데이터베이스 내의 데이터에 접근할 수 있게 하기 위해 관리하는 프로그램

역할

- 데이터 스토리지 - 테이블, 문서, 키-값 쌍과 같은 구조로 데이터 구성
- 액세스 제어
- 백업 및 복구
- 성능 최적화 - 작업 속도를 높이기 위한 인덱싱, 캐싱, 데이터베이스 샤딩
    
    > **캐싱**
    
    자주 요청되는 데이터를 빠른 메모리에 저장해 앱이 기본 DB를 매번 조회하지 않아도 더 빠르게 응답 가능
    
    **왜 사용하는가?**
    쿼리 수가 줄면 부하를 줄이고 DB 인프라를 확장해야 하는 필요성 낮출 수 있음 → 비용도 줄어듦
    
    **이점**
    - 애플리케이션 성능 개선 : 메모리는 디스크보다 훨씬 속도가 빠르게 때문에 인메모리 캐시에서 데이터를 읽는 속도가 매우 빠름(밀리초 미만)
    - 예측 가능한 성능 : 애플리케이션 사용량이 급증하는 시기에 대응할 수 있음. DB 로드 증가하면 데이터 가져오는 데 지연 시간 길어지고 성능 예측 불가능해짐 → 높은 처리량의 인메모리 캐시 활용하면 문제를 완화할 수 있음
    
    **단점**
    - 항상 성능을 개선하는 것은 아님 : 재사용이 적거나 데이터가 자주 바뀌면 캐시 관리 비용만 늘어날 수 있음.
    > 
    
    > **데이터베이스 샤딩**
    
    대규모 DB나 시스템을 ‘샤드’라는 작은 조각으로 나눠 여러 독립된 서버에 분산 저장하고 처리하는 수평 확장 기술
    
    **왜 사용하는가?**
    데이터 볼륨 너무 커지고 동시에 정보 읽거나 저장하려고 하는 사용자 많아지면 DB에서 병목 현상이 발생함. 이로 인해 애플리케이션 속도 느려지고 UX가 안 좋아지기 때문에 여러 샤드에서 더 작은 데이터 세트를 병렬로 처리하면 문제를 해결할 수 있음
    
    **이점**
    - 응답 시간 개선 : 대규모의 단일 DB에서는 데이터를 검색하는 데 시간이 오래 걸림. But 데이터 샤드는 전체 데이터베이스보다 행 수가 적음 → 특정 정보를 검색하거나 쿼리 실행하는 데 걸리는 시간 단축됨
    - 전체 서비스 중단 방지 : 샤드 중 하나를 사용할 수 없게 되어도 대체 샤드에서 데이터에 액세스하고 복원 가능
    
    **단점**
    - 운영 복잡성 : 개발자가 단일 DB를 관리하는 게 아니라 여러 DB 노드를 관리해야 함. 정보 검색할 때 여러 샤드를 쿼리하고 정보를 결합해야 함
    - 인프라 비용 : 조직에서 물리적 샤드로 추가하는 컴퓨터 많을수록 인프라 비용 더 많이 발생함
    > 

### RDB란?

- 상호 연관된 데이터를 테이블 형태로 저장하고 제공하는 데이터베이스
- 특정 규칙에 따라 데이터를 입력, 업데이트, 조회하는 SQL을 사용함

### RDB 특징

- 테이블 중심 구조 : 데이터를 행과 열로 나눠 저장
- 스키마 정의 : 컬럼의 이름·자료형·제약조건 등을 정의하고 데이터를 저장
- 관계 표현 : 기본 키와 외래 키로 데이터 식별하고 테이블 연결
- SQL 활용 : 데이터를 저장·조회·수정·삭제하고, JOIN과 집계로 필요한 정보 구함
- 무결성 관리 : UNIQUE, NOT NULL, 외래 키 등 제약조건으로 데이터 규칙 지킴
- 트랜잭션 지원 : MySQL의 innoDB, PostgreSQL같은 대표적인 RDB 시스템은 여러 변경을 하나의 작업으로 처리

#### 트랜잭션

하나의 논리적인 작업 단위를 안전하게 처리하기 위한 범위

**왜 사용하는가?**
DB의 무결성과 일관성을 보장하고, 여러 작업을 하나의 논리적인 작업 단위로 묶어 처리하기 위해서

**특성 - ACID**

- 원자성(**A**tomicity) : 트랜잭션의 모든 작업이 수행되거나, 아무것도 수행되지 않아야 함
- 일관성(**C**onsistency) : 트랜잭션의 작업 처리 결과는 항상 일관성과 정합성이 보장되어야 함
    
    > **데이터 정합성?**
    서로 다른 테이블에 저장된 데이터 값이 서로 모순 없이 일치하는 상태
    > 
- 독립성(**I**solation) : 트랜잭션 실행 도중 다른 트랜잭션의 영향을 받아 잘못된 결과를 만들어서는 안 됨
- 지속성(**D**urability) : 트랜잭션이 성공적으로 수행되면 결과는 영구적으로 반영되어야 함

### RDB 장단점

**장점**

- 관계 있는 데이터를 관리하기 편함
- 잘못된 데이터의 저장을 제약조건으로 제한할 수 있음
- 중복 줄이고 수정할 위치를 명확하게 할 수 있음

**단점**

- 스키마 변경 관리해야 함
- 인덱스에도 비용 발생
- 동시 변경에서 대기가 발생할 수 있음

### 정규화

RDB의 설계에서 중복을 최소화할 수 있게 데이터를 구조화하는 프로세스

> 이상현상 : 데이터베이스 설계가 잘못되었을 때 발생하는 문제점

- 삽입 이상 : 데이터 삽입할 때 원치 않는 정보까지 입력해야 하는 경우
- 삭제 이상 : 데이터 삭제할 때 관련 정보까지 함께 삭제되어 원치 않는 데이터 손실 발생하는 경우
- 갱신 이상 : 데이터 중복으로 인해 데이터 갱신할 때 일관성 없어지는 경우

→ 이상현상을 없애기 위해 테이블 나누는 작업이 필요함
> 

**1NF** - **도**메인(Domain) 분해
모든 열의 값이 원자값(더 이상 쪼갤 수 없는 하나의 값)을 가지도록 함

**2NF** - **부**분 함수 종속 제거
기본키의 진부분집합이 다른 컬럼을 결정하는 부분 종속을 제거함

**3NF** - **이**행 함수 종속 제거
A→B, B→C가 성립할 때 A→C가 성립하는 이행적 종속 관계 제거함

**BCNF** - **결**정자가 후보키가 아닌 것 제거
함수 종속성 X→Y에서 X가 모두 후보키가 되도록 함

**4NF** - **다**치 종속 제거
하나의 키에 대해 여러 값이 독립적으로 존재하는 다중값 종속성을 제거함

**5N**F - **조**인 종속 제거
릴레이션의 조인 연산 결과가 손실 없이 원래의 릴레이션으로 복원되도록 분리함

### RDB 비교(MySQL vs PostgreSQL) 및 선정 이유

**MySQL**

- 관계형 데이터를 테이블로 관리하며, innoDB에서 트랜잭션과 외래 키 등을 지원함
- JSON 자료형과 검색 기능 제공. 내부 값의 인덱스는 별도 설계가 필요함

**PostgreSQL**

- 관계형 데이터 관리에 더해 사용자 정의 자료형·함수 등 확장 기능을 제공
- jsonb 자료형과 이를 위한 인덱스를 지원함

서비스 상 위치 기반 서비스가 존재하기에 PostGIS를 사용할 가능성이 있고, JSON 컬럼이 존재하므로 JSONB를 통한 정형화를 사용할 수 있어 도입을 고려하였다.

하지만 위치에 기반한 기능은 AI 서버에서만 사용하고, JSON 컬럼으로 들어온 값이 있다고 하더라도 해당 값을 통한 장소 검색 등을 사용하지 않기 떄문에 도입을 하지 않기로 결정하였다.

우리 서비스는 회원, 여행 일정, 방문 장소와 같이 서로 관계가 있는 데이터를 관리해야 하기 때문에 RDB를 선택했다. 
MySQL의 innoDB는 트랜잭션과 외래 키를 지원해, 일정과 방문 장소를 함께 저장하고 데이터 관계를 유지하는 데 적합하다고 판단했다. 또한 JSON 자료형을 제공해 장소마다 항목이 달라지는 부가 정보를 유연하게 저장할 수 있다. 
PostgreSQL도 이러한 요구사항을 충족하지만, 현재 MySQL로 필요한 기능을 구현할 수 있다고 판단해 선택했다.

> **InnoDB란?**
MySQL의 기본 스토리지 엔진
MySQL이 테이블 데이터를 실제로 저장하고 조회, 잠금, 트랜잭션을 처리하는 방식을 담당함
> 

### MySQL 장단점

**장점**

- 테이블과 SQL 기반으로 데이터 관리 : 관계가 있는 데이터를 나눠 저장하고 JOIN으로 함께 조회가 가능함
- 트랜잭션 지원 : 여러 변경을 모두 반영하거나 취소 가능함 (원자성)
- 외래 키 지원 : 존재하지 않는 데이터를 참조하는 저장을 방지할 수 있음
- 행 잠금과 MVCC 지원 : 동시 접근을 제거하고 일반적인 조회와 수정 간 충돌을 줄임
    
    > MVCC란?
    
    데이터의 여러 버전을 관리해, 여러 사용자가 동시에 조회하거나 수정할 때 충돌을 줄이는 방식
    
    But, 같은 데이터를 동시에 수정하거나 잠금 조회를 하면 잠금 대기가 발생할 수 있어 MVCC가 잠금을 완전히 없애는 것은 아님.
    > 
- 기본 키 중심의 저장 구조 : 기본 키를 이용한 데이터 접근에 적합

**단점**

- 잠금 대기와 데드락 발생할 수 있음 : 데드락으로 롤백된 트랜잭션은 안전하게 재시도할 수 있도록 설계하는 것이 필요할 수 있음
    
    > **데드락이란?**
    교착상태. 두 개 이상의 트랜잭션이 서로가 가진 잠금이 풀리기를 기다려, 어느 쪽도 진행하지 못하는 상태
    
    **처리 방법?**
    InnoDB는 기본적으로 데드락을 감지함 → 감지하면 순환 대기를 끊기 위해 하나의 트랜잭션 선택해 롤백함 → 롤백된 트랜잭션은 애플리케이션에서 오류 처리하고 트랜잭션 전체를 재시도할 수도 있음
    
    **방지하기 위해서는?
    -** 트랜잭션 범위를 작게 하고, 필요한 작업 후에 빠르게 Commit 함
    - 여러 테이블이나 행 수정 시 항상 같은 순서로 접근
    >

## 4. 인메모리 DB - REDIS

#### 서비스 설계 상 RDB만 사용하였을 때 발생 가능한 문제와 인메모리 DB 도입 시 이점

요청과 쓰기 작업이 많이 발생하는 기능에서는 RDB를 사용 시 병목이 발생할 수 있다. 또한 저장 가치가 낮고 일정 시간이 지난 후에 만료되는 데이터를 관리하기 위해 RDB를 사용하기보다 인메모리 DB를 도입하는 것이 효율적이다.

현재 서비스 상 이러한 비효율이 발생하는 기능은 다음과 같다.

1. 로그인 세션 관리
    
    Refresh Token은 Access Token Refresh 시마다 서버에 읽기 작업이 필요하고, 이는 토큰 재발급 요청이 증가할수록 부하의 원인이 된다.
    
    인메모리 DB를 이용하면 이러한 읽기 작업의 부하를 많이 줄일 수 있다.
    
    또한 TTL 설정으로 서버에 삭제 명령 없이 자동으로 삭제할 수 있기에 사용 시 동작 구현이 용이하다
    
2. 채팅 서비스
    - 채팅 접속자 수 표시 기능 구현 시
        
        서비스 상 오픈 채팅방에 접속 중인 접속자 수를 표시해야 하는 기능이 존재한다. 이를 RDB로 구현 시 매번 사용자가 접속 상태인지를 최신화 해야하고, 이는 병목이 될 수 있다.
        
        인메모리 DB를 사용할 때에는 Socket이 연결된 사용자를 인메모리 DB에 저장해두고, TTL을 연장하는 방식을 사용하여 비교적 간단하게 구현 가능하다.
        
    - 채팅 도배 방지(RateLimit)
        
        오픈채팅 정책 상 도배 방지 기능이 필요하다. 이를 RDB로 구현하기 위해서는 RateLimt 테이블을 두고, Sliding Window 방식을 사용하여 일정 시간 내에 각 사용자가 보낸 채팅 수를 집계해야 한다.
        
        하지만 이 경우에 집계 쿼리가 계속 동작해야 하기 때문에 리소스 소모가 크다.
        
        이 경우 인메모리 DB인 Redis를 사용 시 Sorted Set과 Lua Script를 이용하여 간단하게 Sliding Window를 이용한 RateLimit을 구현 가능하다.
        

1. 인기 게시물 정렬 기능 구현 시
    
    서비스의 커뮤니티 기능에는 조회수와 좋아요 수를 기반으로 한 인기 순 정렬이나 인기 게시물 상단 고정 등의 기능이 존재한다.
    
    이 때, 실시간으로 게시물들의 게시물 별 인기 점수 공식 계산을 수행하고, 업데이트 및 정렬 작업은 리소스가 많이 소모되는 작업이다.
    
    이를 인메모리 DB를 이용하면 계산 후 빠른 업데이트가 가능하고 Redis등의 인메모리 DB를 택할 시 Sorted Set을 통해 바로 처리가 가능하다.
    

#### 인메모리 DB 선택과 캐싱 전략

Redis를 사용한다.

앞서 살펴본 인메모리 DB가 필요할 만한 기능들을 Redis에서 제공하는 기능들로 구현이 가능하다.

- 로그인 세션 관리
    
    사용자의 Refresh Token을 저장한다. Key - Value 구조를 이용하여 저장하고, TTL 설정으로 토큰의 생명주기를 자동으로 관리한다. 이에 삭제 스케쥴러가 불필요해진다.
    
    이 때, 모든 Refresh Token은 Redis에서 관리하므로 Redis Only 전략을 사용하여 쓰고, 마찬가지로 읽기 시에도 Redis Only Read 방식을 사용한다.
    

- 채팅 접속자 수
    
    Socket에 연결된 사용자를 Redis에 Key - Value 구조로 저장해두고, TTL 설정을 한 후, 사용자의 heartbeat를 받을 때마다 이를 연장시키는 방식으로 현재 사용자 수를 집계한다. 오래된 사용자는 제거 작업을 조회 과정에서 시행하거나 주기적으로 관리한다.
    
    실시간 채팅 접속자 수는 RDB에 저장할 필요가 없으므로 읽기와 쓰기 모두 Redis만을 사용한다(Redis Only).
    
- 채팅 RateLimit
    
    Sliding Window 기법으로 Rate Limit을 적용시킨다. 이 때, Sorted Set을 이용하여 각 메세지를 시간 순으로 배치하고, 도배 제한 시간보다 더 지난 메세지들은 Redis에서 삭제시키고, 남은 메세지들의 수를 집계한 결과가 RateLimit 기준보다 높다면 제재를 적용 시키는 방법을 사용할 수 있다.
    
    채팅의 RateLimit은 초기화되어도 서비스 상 큰 문제가 발생하지 않고, RDB에 저장할 필요가 없으므로 Redis만을 사용한다(Redis Only)
    
- 인기 게시물 랭킹
    
    인기 점수를 기준으로 Sorted Set을 통해 게시물을 저장한다. 이를 통해 주기적으로 게시물 인기 점수를 최신화하여 자동으로 정렬된 게시물 결과를 얻을 수 있다.
    
    인기 게시물의 경우 사용자들이 많이 읽기 작업을 수행하게 된다. 이에 Look-Aside 패턴을 사용하여 캐시를 먼저 조회 후 miss 시 RDB에서 데이터를 가져오도록 한다.
    
    <aside>
    💡
    
    Cache Stampede
    
    Look-Aside 패턴에서는 캐시에 데이터가 없는 경우 DB에서 데이터를 요청 후 이를 다시 캐시에 쓰는 작업을 거친다. 이 때, 여러 서버에서 같은 값을 보고있었을 경우 모든 애플리케이션 서버들이 DB에서 같은 값을  찾게 되는 Duplicate Read가 발생하게 된다. 또한 각각의 DB가 같은 값을 캐시에 저장하는 Duplicate Read도 발생할 수 있다. 이는 비효율적이며 처리량이 늘어나며 비효율적인 동작이 늘어나기에 장애로 이어질 수 있다.
    
    </aside>

## 5. 비동기처리

서비스 상 두 곳에서 AI 서버로부터 결과를 받아오는 구간이 존재한다.

한 곳은 사용자 취향 기반 여행 장소 및 동선 추천. 다른 한 곳은 사용자의 여행 지역에 맞는 AI 포토미션 생성과 사용자 제출에 대한 평가이다.

이런 구간에서 결과들이 빠르게 받아와진다면 비동기 처리를 고려할 필요가 없지만, AI 서버의 부하가 큰 곳, 특히 사용자 포토미션 생성과 평가에 서 이미지 분석이 필요하기 때문에 시간이 오래 걸릴 가능성이 있어 사용자 경험 증대를 위해 비동기 처리를 고려하여야 한다.

기본적인 동작은 다음과 같다. AI 서버에 요청을 보낸 후 먼저 202 ACCEPTED를 반환한다. 이 때, 각 요청과 응답에는 각 요청의 식별 값을 가지고 있어야, 어떤 방식을 사용하더라도 각 요청과 응답을 연결시킬 수 있다.

#### 1. Polling 방식

Polling 방식은 AI 서버에 지속적으로 HTTP 요청을 보내 작업의 현황을 응답받는 방식이다.

이 경우 구현 난이도가 낮아 빠른 개발이 가능해 MVP 개발 시에 이점을 가질 수 있지만, 주기적으로 추가 조회 요청이 필요하다는 단점이 있다.

#### 2. Callback 방식

이 방식은 Polling 방식에서 불필요한 추가 조회 요청이 사라지는 형태이다. AI 서버로의 요청 시에 callback URL을 함께 전송한 후, AI 서버에서 작업을 완료했을 시에 해당 URL로 응답을 보내는 방법이다.

이러한 방식을 위해서는 Callback 인증(공격 방어), 재시도 처리, 중복 요청 처리의 설계가 필요하기에 멱등하도록 요청과 응답 구조를 설계하는 것이 필요하다.

#### 3. Message Queue

Message Queue는 처리해야할 메세지를 중간 저장소에 넣어두고 다른 시스템이 추후에 가져가 처리하는 구조이다.

앞선 방식들은 서버 간 결합이 강하게 이루어져있기 때문에 한 쪽 서버만 잘 못 되더라도 요청 시간이 길어지고, 응답이 늦어진다면 그 응답을 계속 기다려야 하는 단점이 존재한다.

Message Queue를 이용하면 이러한 단점을 해소할 수 있다. 요청을 Message Queue에 메세지를 발행하여 넣어두고, 이 메세지를 AI 서버에서 소비하게 하기 때문에 두 서버 간의 결합도를 낮춰줄 수 있고, 한 쪽 서버가 잘 못 되더라도 요청을 Message Queue에 남아 있으므로 시스템의 안정성이 향상된다.

또한 Message Queue는 트래필 완충(buffering) 역할도 수행할 수 있다. 기존처럼 강한 결합으로 연결되어있던 서비스에서 갑자기 많은 사용자의 요청이 들어오게 될 경우 AI 서버에 과부하가 일어날 가능성이 크다.

하지만 Message Queue에 요청을 쌓아두기만 하면 AI 서버는 가용 가능한 만큼의 작업만 가져가 수행하는 것을 반복할 수 있기 때문에 시스템 안정성이 추가로 증대되는 효과가 있다.

<aside>
💡

Message Queue가 잘 못 되면?

Producer와 Consumer 사이의 중간 통신 경로가 끊기는 것이기 때문에 치명적일 수 있다.

새로운 메세지를 넣을 수도 없고, 기존에 소유하던 메세지도 Consumer가 처리할 수 없게 된다. 이에 Producer는 Message Queue에 작업을 넣는 동작이 실패할 경우 503 에러를 발생시키도록 하여 작업 접수가 불가함을 응답하는 것이 필요하다.

기존에 들어있던 메세지는 설정에 따라 복구할 수 있지만 완벽한 복구는 불가능하기에 여러 Message Queue 노드를 두는 방식을 사용하는 것이 필요하다.(클러스터 구성)

</aside>

Message Queue의 핵심 구성요소는 Producer Broker Consumer로 이루어진다.

Producer는 메세지를 보내는 시스템으로, 현재 서비스에서 도입하게 된다면 Spring이 이 Producer에 해당된다.

Broker는 메세지를 저장하고 전달하는 중간 서버이다. Kafka, Rabbit MQ 등이 존재한다.

Consumer는 메세지를 가져와 실제로 작업을 수행한다. AI 서버가 이에 해당된다.

#### 대표적인 Message Queue

- Rabbit MQ
    
    전통적인 Message Broker. Producer가 메세지를 바로 Queue에 넣지 않고, Rabbit MQ에서는 보통 Exchange를 통해 어떤 Queue로 보낼지를 결정한다.
    
- Kafka
    
    Kafka는 분산 이벤트 스트리밍 플랫폼에 가깝다. 요청 이벤트를 로그처럼 계속 저장 후, 어느 이벤트까지 읽혔는지를 Offset을 통해 관리할 수 있으며, 이벤트 하나를 여러 서비스가 독립적으로 읽는 것이 가능하기에 MSA 환경에서 높은 요청량을 처리할 때 유리하다.
    

#### 우리 서비스에는?

현재 우리 서비스에서 비동기 처리를 도입하고자 하는 이유는 AI 서버에서 받아올 요청을 안정적으로 처리하고, 사용자 입장에서 요청을 기다리지 않도록 하기 위함이다.

MVP 단계에서부터 명확한 필요성 없이 Message Queue를 도입하기보다는, 현재 RDB에 설계되어 있는 **멱등성 키(`idempotency_key`)를 활용해 중복 요청을 방지**하고, I**/O 대기 작업은 Virtual Thread 기반으로 처리하는 방식**을 적용하고자 한다. 이를 통해 별도의 메시지 브로커 없이도 단순한 구조로 높은 동시성을 처리할 수 있으며, 추후 사용자 증가로 인해 높은 처리량이 요구되거나 작업 적체, 재시도, 메시지 유실 방지 등 비동기 작업의 내구성이 중요해질 경우 RabbitMQ 도입을 고려하는 것이 적합하다고 판단하였다.

## 6. 오픈 채팅 구현

## HTTP 요약

클라이언트와 서버가 데이터를 주고받기 위한 **요청(Request) → 응답(Response) 기반의 애플리케이션 계층 프로토콜**

HTTP는 클라이언트의 요청에 따라 서버가 응답하는 구조를 가지고 있기 때문에 실시간 채팅에 적합하지 않다.

물론 채팅을 구현할 수 없는 것은 아니다.

#### Polling 방식을 통한 채팅 구현

서버는 메세지가 생기는 즉시 클라이언트에게 알려줘야한다. 하지만 서버는 클라이언트에게 정보를 보낼 수 없기 때문에 클라이언트는 메세지가 왔는지 일정 시간마다 요청을 보내는 Polling 방식을 사용해야 한다.

이런 방식으로 채팅을 구현 시에는 새로운 채팅 메세지가 없더라도 요청이 계속 발생하여 쓸데없는 요청이 매우 많이 발생하게 되어 병목이 발생한다.

또한, Polling 시간에 따라 새로운 메세지들을 응답받기 때문에 실시간성을 보장받기 어렵다.

실시간성 ↔ 요청량은 트레이드 오프.

## WebSoket이란?

 클라이언트와 서버 간에 지속적인 연결을 유지하며 **양방향 통신 (Full-Duplex)**을 가능하게 하는 프로토콜

HTTP 통신과는 다르게 연결을 유지하고, 서버도 클라이언트에게 요청 없이 데이터를 보낼 수 있다.

⇒ **Full-Duplex, 전이중 통신**

WebSocket 연결은 HTTP로 시작되고, WebSocket Handshake이후 WebSocket으로 전환된다.

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
```

클라이언트가 서버에게 이런 요청을 보내면

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

서버는 이렇게 응답하여 통신 프로토콜을 변경한다.

이후 WebSocket Frame을 이용하여 데이터를 주고받는다.

이제 서버가 클라이언트에게 요청 없이 정보 전달이 가능하므로 Polling 방식을 사용하지 않아 Polling의 단점을 해소할 수 있다.

#### 장점

- 서버가 클라이언트에게 즉시 Push 가능
- 연결을 유지하므로 HTTP 요청 비용이 줄어듦
- 낮은 지연시간
- 전이중 통신

#### 단점

- 연결을 계속 유지해야 한다
    
    유저가 10만명이라면 10만명의 연결을 모두 유지해야 한다.
    
- 메세지 처리 규칙을 제공하지 않는다.
    
    WebSocket은 데이터를 전달할 뿐이고, 그 데이터가 무슨 데이터인지는 알지 못한다.
    
    이에 이러한 규칙을 개발자가 직접 설정해야 한다
    
- 서버 확장이 까다롭다
    
    일반 HTTP 연결은 서버 확장 시 로드벨런서를 이용하여 처리할 수 있지만 WebSocket 연결 시에는 각 서버에 연결이 유지되기 때문에 메세지 전달 설계가 추가로 필요하다.
    
    이 때 사용하는 것이 Redis Pub/Sub, Kafka, RabbitMQ이다.
    

## STOMP(Simple Text Oriented Messaging Protocol)

메세지를 주고받는 형식을 정의한 메세징 **프로토콜**

WebSocket과 대응되는 기술이 아니고, 그 연결 위에서 메세지 송신시  규칙을 제공하는 역할을 한다

앞서 말한대로 WebSocket은 전달받고 전달하는 데이터가 무슨 데이터인지 알지 못한다. 이에 서버에서 해당 메세지 처리 규칙을 만들어야 하는데, 그 역할을 하는 것이 STOMP이다.

STOMP는 메세징 규칙을 destination 기반으로 표현 가능하다.

```
클라이언트: /app/chat/10 으로 메세지 전송

사용자:/topic/chat/10 해당 destination을 구독
```

#### SEND와 SUBSCRIBE

채팅에서는 보통 두 가지 동작이 핵심이다. SEND와 SUBSCRIBE.

어떤 destination을 구독 중인 사용자들이 있고, 어떤 사용자가 그 destination으로 메세지를 전달하면 구독자들에게 해당 메세지를 전달한다.

Spring에서는 STOMP 사용 시 

```java
@MessageMapping("/chat/{roomId}")
@SendTo("/topic/chat/{roomId}")
public ChatMessage send(
        @DestinationVariable Long roomId,
        ChatMessage message
) {
    return message;
}
```

이러한 식으로 표현된다.

#### STOMP Frame

STOMP에서는메세지를 Frame 단위로 주고받는다.

Frame은 COMMAND, HEADER, BODY 구조를 갖고, 

COMMAND에는 다음과 같은 것들이 존재한다.

```java
CONNECT
SEND
SUBSCRIBE
MESSAGE
DISCONNECT
```

#### 장점

- WebSocket 위의 메세지 통신을 규칙화해준다.
- 목적지 기반 라우팅이 명확하다.
    
    메세지를 어디로 보내고, 어디를 구독할지 명확하게 표현할 수 있다.
    
- 구독 모델 구현이 편하다.
    
    Pub/Sub 구조를 자연스럽게 표현 가능하다
    
- Spring에서 STOMP 구현이 쉬움.
    
    기존 RESTContoller를 만들것 것과 비슷하게 표현 가능하여 개발 편의성이 높다.
    
    ```java
    @MessageMapping("/chat")
    public void send(ChatMessage message) {
    }
    ```
    
- 메세지 관련 기능이 이미 정의되어 있다.
    
    결, 전송, 구독, 구독 해제 같은 동작을 위한 공통 규약이 있다.
    

#### 단점

- 추가적인 오버헤드 발생
    
    순수 WebSocket은 단순하게 데이터만 보낼 수 있다. 하지만 STOMP는 여기에 destination, content-type인 COMMAND, HEADER 데이터가 추가된다.
    
    ⇒ 순수 WebSocket보다 네트워크 오버헤드와 파싱 비용이 조금 더 발생
    
    이에 극도로 높은 처리량이나 낮은 지연 시간이 중요한 시스템에서는 이러한 단점을 고려해야 한다.
    
- 프로토콜 계층의 증가
    
    ```java
    TCP																		TCP
    ↓																			↓
    WebSocket															WebSocket
    ↓																			↓
    Application														STOMP
    																			↓
    																			Application
    ```
    
    이렇게 중간에 STOMP 프로토콜 계층이 추가되어 이해해야할 개념이 많고, 문제 발생 시에도 고려해야할 부분이 늘어난다. ⇒ 관리 포인트가 증가한다
    
- 커스텀 프로토콜에서의 제약이 될 수 있다.
    
    STOMP는 정해진 메세징 모델을 사용하기 때문에
    
    극도로 작은 패킷, Binary 중심 통신, 자체 메세지 코드, 매우 높은 빈도의 통신이 필요할 경우 순수 WebSocket으로 자체 프로토콜을 만드는 것이 더 적합할 수 있다.
    

## Socket.io

실시간 양방향 통신을 쉽게 구현하기 위한 **라이브러리/프레임워크 계층**

> Socket.IO != WebSocket
> 

Socket.IO는 내부적으로 WebSocket을 사용할 수 있지만, 여기에 **재연결, 이벤트 기반 통신, fallback, room, namespace 같은 기능을 추가로 제공**

Socket.IO는 보통 클라이언트와 서버가 연결된 뒤, **이벤트 이름 + 데이터** 형태로 통신

```java
//서버
socket.emit("chat-message", {
  roomId: 10,
  message: "안녕하세요"
});

//클라이언트
socket.on("chat-message", (data) => {
  // 메시지 처리
});
```

STOMP의 destination 기반 방식과 달리, Socket.IO는 **이벤트 기반(event-driven)** 통신이 중심

WebSocket에서 메세지를 직접 해석할 수 있는 규칙을 제정해야 하는 것과는 다르게

Socket.io는 통신을 여러 이벤트로 나눌 수 있다.

```java
socket.on("join-room", ...);
socket.on("chat-message", ...);
socket.on("typing", ...);
```

이에 애플리케이션 코드가 직관적이다.

#### Room 기능

Socket.io가 채팅에서 편리한 이유 중 하나는 Room 기능

사용자가 채팅방에 진입하고 전체에 메세지를 보낼 때,

```java
socket.join("room-10");

io.to("room-10").emit("chat-message", message);
```

라고 작성하여 구현 가능하다.

⇒ 채팅방을 직접 구현해야 하는 부담이 줄어든다

#### 자동 재연결

Socket.io는 연결이 끊겼을 때 재연결을 위한 기능도 기본적으로 제공한다.

순수 WebSocket을 사용하면 이런 재연결 정책을 직접 구현해야 하는 경우가 많다.

#### WebSocket 미지원 시 Long Polling으로 대응

환경에 따라 HTTP Long Polling을 사용 후 WebSocket으로 업그레이드 하는 방식이 가능하므로, 네트워크 환경에 대한 대응력이 좋다.

<aside>
💡

Long Polling

일반적인 Polling에서 발전된 기법에서 클라이언트의 정보 요청 시 보낼 정보가 없다면 해당 응답을 유예시킨 후 보낼 정보가 있을 때 응답을 돌려주는 방법이다.

</aside>

#### 주의점

Socket.io 클라이언트는 자체 프로토콜과 메세지 형식을 이용하기 때문에 일반 WebSocket 서버에 그대로 연결할 수 없다.

이에 Socket.IO Client ↔ Socket.IO Server 형태로 상요한다

#### STOMP와의 비교

두 기술 모두 WebSocket위에서 개발 편의성을 높여주지만 접근 방식이 다르다.

STOMP → destination / subscribe 중심

Socket.IO → event / room 중심

#### 장점

- 가장 큰 장점은 실시간 통신 개발을 매우 빠르고 편하게 할 수 있다는 점.
- 이벤트 기반 API가 직관적이다.
    
    채팅, 입장, 퇴장, 타이핑 등의 동작을 이벤트 기반으로 나누기 쉽다.
    
- Room 기능이 편리하다
    
    채팅방 단위로 사용자를 묶고 해당 방에만 메세지를 보낼 수 있기 때문에 채팅방 라우팅을 바닥부터 구현할 필요가 줄어든다
    
- 재연결 처리 지원
    
    앞서 말한 대로 네트워크 유실 시 자동으로 재연결을 실시하기 때문에 모바일 채팅 서비스에서 꽤 유용하다.
    
- 실시간 기능 개발 속도가 빠르다
    
    채팅 MVP처럼 빠르게 구현해야 할 때는 순수 WebSocket보다 생산성이 높다
    

#### 단점

- 표준 WebSocket과 호환되지 않는다.
    
    자체 프로토콜 사용으로 Socket.io의 생태계에 맞춰야한다.
    
- 추가적인 오버헤드 발생
    
    구조산 단순 Websocket 위에 자체 프로토콜과 이벤트 관리 기능이 얹히므로 순수 WebSocket보다 패킷과 처리 구조가 무겁다
    
- Spring 생태계와는 STOMP만큼 자연스럽지 않다.
    
    Node.js에서는 Socket.IO가 자연스럽지만 Spring에서는 보통 WebSocket + STOMP 조합이 더 일반적이다.
    
- 대규모 서버 확장 시 추가 구성이 필요하다
    
    한 채팅방에 있는 사용자가 서로 다른 서버에 있다면 서버 간 이벤트 전달이 필요하기 때문에 Redis Adapter같은 방식으로 서버간 메세지 동기화를 하는 구성이 추가될 수 있다.
    

## Netty

Java 기반의 고성능 네트워크 프레임워크

> TCP, HTTP, WebSocket 같은 네트워크 통신을 직접 구현할 때 필요한 복잡한 소켓 처리, 스레드 관리, 비동기 I/O 처리를 편하게 해주는 라이브러리
> 

전통적인 서버에서는 연결 하나 당 하나의 쓰레드를 사용하였기 때문에 쓰레드 생성과 Context Switching 비용이 많이 발생하였다.

이러한 문제를 해결하기 위해 Netty는 Non-blocking I/O를 기반으로 하나의 EventLoop 쓰레드가 여러 네트워크 연결을 관리한다.

즉, 적은 수의 쓰레드로 많은 수의 연결을 처리할 수 있다.

채팅 서버는 한 번 연결을 하면 이 연결을 오랫동안 지속하기 때문에 이러한 서비스를 제공할 경우 Netty를 사용하는 것을 고려할 수 있다.

Netty는 저수준 네트워크 제어 기능을 제공하는데, 이는 대규모 WebSocket 연결 시에 응답 시간을 줄이고, 안정적인 연결을 가능하게 하므로, 추후 서비스가 확장되는 경우 도입을 검토할 수 있다.

초기에는 구현해야할 분량이 매우 많아지게 되므로 사용자가 적은 상황에서는 오버엔지니어링이 될 수 있다고 생각한다.

## 우리 서비스에는?

#### 고려할 점

1. 오픈 채팅만 존재한다
2. Spring을 서버 개발 프레임워크로 사용한다
3. 추후 대규모 서비스에서의 확장 가능성을 염두하여야 한다

오픈 채팅만 존재하므로 Socket.IO를 고려해볼 수 있지만, V1 배포에서 MVP 기능 개발 속도도 고려해야 하고, Spring 프레임워크를 사용할 예정이므로 이 점도 고려하여야 한다.

이에 WebSoket + STOMP를 이용하여 채팅 서비스를 구현 후 추후 서비스가 확장되거나 부하 테스트 후에 성능 개선이 필요하다면 Netty의 도입을 검토해야 할 것이다.
